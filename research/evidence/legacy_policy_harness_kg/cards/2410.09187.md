## Main point

ProgressCounts turns an LLM-generated, simulator-state progress projection into a stateful count bonus and reports `0.59` mean success over 20 BiDex tasks with four `100M`-sample policy candidates per task, but the executable reward is the whole progress/discretization/count/update runtime—not the generated progress function alone—and the public code differs materially from the paper's compact equation.

## Mechanism

```mermaid
flowchart LR
    T[Input<br/>short task description] --> L[GPT-4-Turbo<br/>progress-function generator]
    S[Input<br/>simulator state-feature description] --> L
    H[Frozen per benchmark<br/>helper-function library] --> L
    L --> P[Generated output<br/>P(s): progress scalars + directions]
    P --> D[Frozen heuristic D<br/>range estimate + ordered granularity]
    D --> B[Discrete progress bin B(s)]
    B --> C[Stateful visit count c(B)]
    X[Frozen sparse success signal] --> R[Executable output<br/>task_reward_k]
    C -->|novelty 1/sqrt count| R
    R --> F[Frozen world + observations + actions<br/>dynamics + controller + PPO + budget]
    F --> K[Trained policy candidate]
    K --> E[Frozen task-success evaluator]
    E --> Q[Select highest-success<br/>of 4 candidates]
    E -. evaluation feedback only;<br/>no reward-revision loop .-> Q
```

## Executable reward contract

| Layer | Paper | Pinned BiDex archive | Consequence for Sam |
| --- | --- | --- | --- |
| Progress output | `P:S→R^k`; one or more scalar subtask variables plus increase/decrease booleans | Task modules embed Python `progress_function` methods and pass their tuple in `infos['binning']` | Generated code needs typed, whitelisted inputs and immutable source/runtime identity |
| Discretization | Estimate each variable's range; use finer bins for later subtasks; `B(s)=D(P(s))=Σx'_i` | First call caches a minimum or maximum; each term is `long(progress_i * (1000 * is_last + 20)) % 10000`; terms are added | Cache initialization, numerical guards, scale factors, collision behavior, and modulo are part of `task_reward_k` |
| Novelty | `n(s) ∝ 1/√c(B(s))` | `1/sqrt(global_count[bin]+1)`, computed before the current batch increments the count | Count scope and update order are semantic, not trainer bookkeeping |
| Reward | Sparse reward plus `lambda_c n(next_state)` | Normalize the current batch bonus to mean `0.001`, clip to `[0,0.1]`, then set `reward[:,0] = 0.05*success + bonus` | The code replaces the passed reward column; it does not merely append the paper's symbolic term |
| Trainer interface | PPO consumes the augmented task reward | RL-Games expects success, progress tuple, and done information; code allocates CUDA counts and assumes `2048` environments for auxiliary state | The interface must be admitted and frozen before comparisons; per-candidate trainer edits confound the reward knob |

## What transfers to Sam's harness

- Admit `P + D + count state + initialization + update order + sparse-success term + normalization/clipping` as one immutable executable `task_reward_k`. Hashing only LLM output `P` is insufficient.
- Restrict generated progress code to a typed allowlist of already-frozen observation/state fields and pure helper functions. Validate shapes, directions, finite outputs, range behavior, bin bounds, collisions, and negative paths before launch.
- Expose one predeclared reward-runtime interface from the fixed trainer: progress values, success, termination, count scope, reset behavior, and cadence. Use the same implementation for every reward candidate.
- Persist requested reward settings separately from observed runtime facts: installed code hash, actual bin mapping, initialized extrema, count-state checksum/checkpoint, update order, mean normalization, clipping, and the exact sparse-success evaluator.
- Freeze world, observations, actions, dynamics, controller, tracking reward, PPO settings, seeds, samples per candidate, candidate count, and checkpoint rule. Treat four-way selection as part of the budget.
- Select with immutable training/selection evidence, then report objective task success on fresh seeds and perturbations not exposed to the generator or selector.
- Keep task success independent of the generated reward. Progress is a proposal for exploration state; it is not an objective evaluator.

## What does not transfer

- The paper does not select, order, transition, blend, or certify reference motions. It is not evidence for Sam's reference composition/oracle knob.
- A progress function is not policy conditioning and supplies no immutable playback clock to actor or critic.
- The broad prompt permission to access any member of simulator `self` is not an admissible execution boundary for uploaded/generated code.
- Simulation-state distances do not establish deployability from physical observations, real-robot transfer, contact safety, naturalness, perturbation recovery, or calibrated confidence.
- The paper fixes PPO and standard task settings for its comparisons, but its reward shaper requires a special trainer interface and state. It is not a drop-in reward for an arbitrary frozen trainer.
- The `2B` TwoCatch result does not support a fixed-total-budget comparison after selecting the best of four such runs.
- The public archives do not establish a fully automated, versioned reproduction of LLM generation and all tables.
- No claim here is evidence that RL-Sculptor implements ProgressCounts.

## Failure modes and caveats

- **Direct-progress brittleness:** summing progress as a dense reward falls from `.59` to `.45`, consistent with scale/weight sensitivity.
- **Generic-state hashing:** SimHash over observations reaches `.34` versus `.59` for progress bins.
- **Feature-library omission:** CatchUnderarm falls from `.76` to `0`; the generated function averages an irrelevant object-velocity feature into progress.
- **LLM range error:** asking the LLM to emit bins makes SwingCup fall from `.97` to `0` after it guesses ineffective feature ranges.
- **Stateful, path-dependent reward:** global counts and first-call extrema make reward depend on prior visitation, batching, and initialization; a scalar function of the current transition is not equivalent.
- **Paper/code binning mismatch:** the paper alternates between a `1000` default and `1020` two-stage bins; released code adds scaled integer terms, uses `1020` for the last-stage multiplier, and permits collisions instead of a Cartesian `20×1000` encoding.
- **Paper/code reward mismatch:** Equation 1 adds a weighted novelty term to sparse reward; released BiDex code normalizes by the live batch, clips, and overwrites `reward[:,0]` with success plus novelty.
- **Unequal ablation replication:** main ProgressCounts values use five trials; ProgressAsReward and SimHashCounts use one.
- **Selector leakage:** the highest-success policy sample is selected from a single training run and success is also the paper's endpoint metric; no untouched selection split is described.
- **Paper table inconsistency:** Kettle is `.83` in Table 1 but `.99±.01` in Appendix Table 8 for ProgressCounts.
- **Mutable partial release:** the Drive files have no release tag or immutable public commit; instructions require manual task/wrapper editing, and the official project page still says “Code (coming soon).”
- **Hard-coded release variants:** some task modules invoke ablation functions rather than their default `progress_function`, so the archive is not one clean main configuration.
