## Main point

On the state-based H1-plus-Shadow-Hands runtime, three-seed flat-policy baselines stayed below the authors’ qualitative return target on most tasks; because that target and reported return reuse the training reward, while the stronger hierarchical baseline changes the action/controller and adds billions of pretraining steps, HumanoidBench is evidence for a fixed evaluation surface and failure taxonomy—not for an oracle-only or reward-only improvement.

## Mechanism

~~~mermaid
flowchart LR
    T[Task ID + reset distribution] --> E[FROZEN benchmark runtime<br/>MuJoCo, H1 + 2 Shadow Hands<br/>state observation, dynamics, horizon]
    E -->|state observation| P[Flat learner<br/>DreamerV3 / TD-MPC2 / SAC / PPO]
    P -->|61-D joint-position targets at 50 Hz| E
    E -->|task reward + next state + termination| P
    E --> R[Episode reward sum]
    R --> Q[Task-specific qualitative target]
    Q --> O[Three-seed curves and return tables]
    H[HRL ablation<br/>high-level 3-D or 6-D setpoints] --> L[FROZEN pretrained reaching policy]
    L -->|joint targets| E
~~~

## Task-reward and evaluation boundary

- **Reported fact:** Episode return is the sum of the environment’s training reward. Dashed task-success lines are qualitative return targets, not a separately validated objective metric.
- **Harness implication:** If Sam changes <code>task_reward_k</code>, the paper’s return and target no longer remain invariant. A reward-search experiment needs frozen task-state success predicates, subtask completion, safety, stability, and naturalness measures outside the edited reward.
- **Reported fact:** The pinned code exposes task-specific success fields for some tasks, including push and package, but the paper reports return tables rather than a suite-wide success-rate protocol.
- **Boundary:** HumanoidBench supplies executable seed rewards and candidate objective predicates. It does not present reward generation, reward editing, or reward selection.

## What transfers to Sam's harness

- Pin the complete benchmark identity: code commit, robot, task variant, reset distribution, observation/action names and shapes, control mode/rate, physics, reward, termination, and episode horizon.
- Use the 27-task surface to test whether a reward or oracle improvement transfers beyond one MDP. Preserve the same trainer and per-task budget within each comparison family.
- Keep the paper’s reward return as a diagnostic only when <code>task_reward_k</code> changes. Promote task-state success, subtask progress, falls, contacts, stability, and compute to frozen evaluators.
- Retain failure traces, not only best checkpoints. Highbar contact-holding, door partial completion, hurdle collision, and package non-lifting expose different mechanisms behind similar low return.
- Report both central performance and best-checkpoint behavior. The flat push average/max split shows that a successful checkpoint does not establish robust training performance.

## What does not transfer

- The paper contains no reference dataset, reference composition, playback clock, oracle state machine, guards, or recovery transitions.
- The hierarchical baseline is not an allowed reference-composition edit. It replaces the high-level action with reaching setpoints, installs a separately pretrained low-level controller, simplifies pretraining dynamics, and adds <code>2B–4B</code> steps.
- The hand-action ablation changes the action space and therefore defines a new fixed-trainer family rather than an oracle or task-reward candidate.
- The rewards are hand-authored benchmark definitions; the paper does not search, generate, repair, or rank executable reward code.
- Implemented vision and tactile observations are not measured policy evidence. Hardware transfer and sim-to-real success are not evaluated.

## Failure modes and caveats

- **Highbar:** the agent maintains bar contact to avoid termination but does not execute the whole-body rotation, despite dense reward.
- **Door:** it turns the hatch but fails to coordinate arm pulling with backward whole-body motion.
- **Hurdle:** it reaches the requested speed but adopts stable collision poses instead of exploring a jump.
- **Package HRL:** the reaching prior improves approach behavior but the policy still struggles to lift; the low-level skill never experienced lifting.
- **Dimensionality:** zeroing <code>42</code> hand actions accelerates learning while retaining observations and mass, so action-interface changes can dominate reward/oracle comparisons.
- **Budget comparability:** approximately equal wall time yields <code>10M</code> versus <code>2M</code> steps across algorithms. This is not a matched environment-step comparison.
- **Metric coupling:** reward return and the qualitative success target are not independent of the task reward. They cannot certify an edited reward without an external evaluator.
- **Statistical scope:** curves use three seeds and standard deviations; seed identities, confidence intervals, and hypothesis tests are not reported.
- **Simulation scope:** the altered Shadow-Hand morphology is explicitly described as not currently realistic; experiments are state-based and simulation-only.
- **Aggregation wording:** Appendix C-C first says it reports maximum episode returns, then labels Table V “Average returns” and Table VI “Maximum returns”; the captions are the safest source for metric identity.
