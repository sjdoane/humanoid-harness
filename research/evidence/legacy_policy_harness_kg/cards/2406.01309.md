## Main point

With each task's world and trainer held fixed, REvolve's island search produced executable rewards whose policies beat the human-feedback Eureka baseline in fresh human Elo comparisons on all three simulated tasks; it supplies no reference-oracle mechanism, and the pinned public code does not reproduce the reported human-feedback loop or training budgets as shipped.

## Mechanism

```mermaid
flowchart LR
    I[INPUT<br/>task text + allowed observation/action variables] --> G[GPT-4 Turbo reward designer]
    D[Reward database D<br/>(R, policy, fitness, text feedback)] -->|fitness-weighted island + parent sampling| G
    G -->|mutation: one parent/component<br/>crossover: two parents/components| R[Executable Python task reward]
    Z[FROZEN PER TASK<br/>MDP + simulator + policy algorithm<br/>hyperparameters + training budget] --> T[Train one policy per reward]
    R --> T
    T --> O[Policy rollout videos]
    O --> H[Human pairwise preference<br/>+ checkbox feedback]
    H -->|Elo fitness + NL feedback| D
    D -->|highest fitness| Q[OUTPUT<br/>best policy and recoverable task reward]
```

## Evaluation

Fresh evaluators, disjoint from training, ranked the best policies. All entries began at Elo 1500.

| Task | REvolve | Eureka | Other boundary |
| --- | ---: | ---: | --- |
| Autonomous driving | `1575` (rank 2) | `1499` | Human driving `1586` |
| Humanoid locomotion | `1586` (rank 1) | `1557` | Expert reward `1407` |
| Adroit hand | `1594` (rank 1) | `1522` | Expert reward `1415` |

On unseen AirSim environments, REvolve scored `0.86 ± 0.03` and `0.68 ± 0.04`, versus Eureka's `0.73 ± 0.04` and `0.57 ± 0.05`. The operator ablation reports `mutation + crossover > crossover only > mutation only`; no exact ablation values are tabulated.

## What transfers to Sam's harness

- Treat `task_reward_k` as a typed, immutable executable artifact: allowed state/action inputs, scalar total, named component diagnostics, source text, model/prompt version, and hash.
- Freeze the MDP, simulator, policy initialization protocol, trainer, hyperparameters, budget, and evaluation cadence for reward-candidate comparisons. REvolve changes the reward program, not the inner trainer.
- Keep scalar selection fitness and natural-language mutation guidance as separate feedback channels. Preserve the compared rollouts and exact Elo update order as lineage.
- Retain multiple reward lineages instead of only the current best. Compare mutation, crossover, and both under equal candidate budgets.
- Use a disjoint evaluator after search. REvolve's final human comparison used evaluators not involved in training.
- Sandbox and statically validate generated reward code before launch. The public release directly executes generated Python and is not a trust boundary.

## What does not transfer

- REvolve does not select, splice, schedule, or condition on reference motions; it provides no reference composition, playback clock, phase oracle, predicate, or OGMP mechanism.
- The paper returns the fittest trained policy. Sam's harness must separately preserve and return the reward artifact if `task_reward_k` is the authorable output.
- Results do not establish portability across controllers, optimizers, simulators, observation contracts, training budgets, or hardware.
- Simulation results are not real-world or dynamics-certificate evidence; real-world use is future work.
- The paper and release do not establish safe execution, deterministic replay, immutable manifests, or RL-Sculptor implementation.

## Failure modes and caveats

- Search is expensive: every candidate trains a policy; only two random seeds are reported. The database adds about `2.5 GB` per generation (`17.5 GB` after seven).
- Human-detail matters. Sparse automatic feedback underperformed richer human feedback on Humanoid and Adroit; improvements stabilized around generation 5.
- AirSim generalization degraded in heavier traffic; the authors attribute some failures to the visual module missing oncoming cars. MuJoCo generalization variants were not tested.
- The authors identify closed-source GPT-4 dependence and untested real-world applicability as limitations. The selected policy is explicitly not guaranteed optimal.
- Paper Table 1 says the Adroit observation is 39-D, while Appendix A.1.3 says 97-D. Exact interface reconstruction therefore fails without resolving the environment version.
- The latest code defaults differ from the paper (`15` vs `16` candidates; `4` vs `13` islands; `1,000` vs `5e6` MuJoCo steps). The README also says the AirSim setup is not released.
- The public main loop evaluates candidates from velocity logs. Human Elo processing is a separate script that imports a nonexistent `RewardsDatabase` symbol, so the reported human-guided loop is not runnable end to end from the pinned snapshot without repair.
- Generated code is passed to Python `exec` after only argument/return checks. Do not treat the release as safe executable-reward infrastructure.
- The released Elo script updates comparisons sequentially and then min-max normalizes within the current pool; exact fitness depends on comparison order and pool composition.
